## 4. 当前阻塞的准确描述

本机 `rustc 1.97.0` 默认 target 是 `x86_64-pc-windows-gnu`。`cargo check` 成功，但链接 Wasmtime library 时，`windows-sys` 需要 `dlltool.exe` 调用 GNU `as.exe` 生成 import library；当前 Rust toolchain 只带 `dlltool.exe`、`ld.exe` 与 GCC driver，没有 standalone `as.exe`。因此：

```text
error: error calling dlltool 'dlltool.exe': program not found
```

已安装的外部 Wasmtime 46.0.1 CLI 不能注入 prototype 所需的 typed `host-run` import，不能替代 in-process runner。不要把 `cargo check` 写成“原型已运行”，也不要把工具链缺件写成 Sico 架构失败。

## 5. 接手后的推荐顺序

1. 在具备完整 MinGW binutils 的 Windows host，或可链接 Wasmtime 46.0.1 crate 的 Linux host 上运行：

   ```powershell
   cargo run --release --manifest-path .\prototypes\script-profile\Cargo.toml --locked
   ```

2. 将 stdout JSON 与 host/Rust/Wasmtime/target/CPU/RAM 元数据保存为不可变 report evidence；六个 case 未全部通过时先修原型。
3. 构造 hard-coded guest Program，真实执行 Canonical ABI lift/lower 与 guest memory/realloc。
4. 构造 versioned Adapter 并尝试 Component composition；使用相同 case 对比 composed path 与 direct path。
5. 按 RFC-0029 的门槛比较 correctness、cold/warm latency、peak RSS、artifact size 和 tool stability。
6. 只有得到实测结果后，才接受/修订 RFC-0029 与 ADR-0009，并动态调整 STEP-0077–0084。

## 6. 动态优化 M1–M9 的规则

- M1/M2 只在 Script 案例暴露 parser/semantic 缺口时增加回归，不重开已通过的阶段。
- M3/M4 是 M8 主要复用层；任何 Component/package 变化必须保持旧 scalar manifest 与 Runtime 兼容。
- M5–M7 的 Host、registry、trust 状态不因 M8 原型自动升级；公网生产仍等待外部部署输入。
- M8 的排序由 STEP-0076 实测决定：composition 稳定则进入 Adapter 路线，不稳定则选择同 WIT direct runner fallback。
- M9 继续保持 planned-after-M8；streaming/async/HTTP/REPL 不得混入 M8 bounded batch MVP。

## 7. 不得误报

- M8 未完成，STEP-0076 也未完成。
- direct runner 当前是编译通过的候选，不是已验证架构。
- Adapter composition、Canonical ABI aggregates、`sico run`/`eval`、cache 和标准库尚未实现。
- M6 Android、M7 public production、真实第三方与 live-model 证据仍保持原 gate。
- 不得为获得好看的性能数字而省略 trust、capability、limit 或 Component validation。
