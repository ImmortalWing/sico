## 1. 一句话状态

direct-runner 纵向原型已修复并真实运行：六个机器用例全部通过，原始 JSON、环境元数据与内存采样已存入不可变证据 [`script-profile-prototype-v0.md`](../reports/script-profile-prototype-v0.md)；原型已改为自包含 Program Component（硬编码 guest Core Wasm + 真实 Canonical ABI lift/lower）。Program/Adapter composition 实验与架构裁决尚未执行，STEP-0076 保持 `in-progress`。

## 2. 本轮已经完成

- 链接阻塞已绕过：本机 `1.97.1-x86_64-pc-windows-gnu` 缺 standalone `as.exe`（`dlltool.exe` 无法生成 import library），但已安装 VS 2022 BuildTools（MSVC 14.44）+ Windows SDK 10.0.26100 + `1.97.0-x86_64-pc-windows-msvc` 工具链；用 `RUSTUP_TOOLCHAIN=1.97.0-x86_64-pc-windows-msvc` 成功构建并运行原型。
- 修复原型三处真实缺陷（详见证据报告的 Encoding findings）：
  1. `wasm-encoder` 从 `=0.253.0` 降到 `=0.251.0`，与 Wasmtime 46.0.1 的 wasmparser 对齐；
  2. 原"顶层匿名类型 + func import"违反 wasmparser named-types 规则；改为 types-only instance（`sico:script/types@0.1.0`）逐个命名导出类型，后续声明引用导出索引；
  3. Wasmtime 46.0.1 不支持再导出导入函数（`reexport of an imported function ... not implemented`），放弃"导入 host-run 模拟 guest"，改为硬编码 guest Core Wasm（新增 `wat = "=1.251.0"` 依赖）+ `canon lift`；lift 结果超宽时 core 函数返回单个 i32 结果区指针。
- 原型值形状对齐冻结 WIT：`arguments`/`exit-code`/`code` 字段名与 `script-error-code` 四枚举值（invalid-input/resource-limit/domain-error/cancelled）。
- 六用例真实通过（Unicode args、二进制 stdin、通道分离、exit=7、结构化错误、1 MiB roundtrip、8 MiB+1 拒绝），cold 9.98–21.02 ms（4 个 Component 合计）、warm median ≈0.09–0.11 ms、P95 ≈0.12 ms，采样峰值 RSS ≈81.4 MiB；原始证据见 [`script-profile-prototype-v0.md`](../reports/script-profile-prototype-v0.md)。
- 两份接手文档的仓库路径已改为相对路径 `.`。

## 4. 原阻塞的最终状态

第 4 节旧描述（Windows GNU 工具链缺 `as.exe` 导致 `error calling dlltool 'dlltool.exe': program not found`）在本机仍然成立，但已不再是阻塞：MSVC 工具链可链接 Wasmtime 46.0.1 crate 并完成全部原型运行。若未来需要 gnu 工具链证据，须先安装完整 MinGW binutils 或换 Linux host；不得把 gnu 工具链缺件写成 Sico 架构失败，也不得把 MSVC 结果冒充 gnu 结果（证据报告已如实记录 target）。

## 5. 接手后的推荐顺序

1. 构造 versioned Adapter 并尝试 Program/Adapter composition；用相同六个 case 对比 composed path 与 direct path（correctness、cold/warm latency、peak RSS、artifact size、tool stability）。
2. 按 RFC-0029 的门槛对照两条路径的实测结果，形成 GO/fallback 裁决；只有得到实测结果后，才接受/修订 RFC-0029 与 ADR-0009。
3. 为 guest Program 增加 Canonical ABI 随机化 roundtrip 属性测试（host Val ↔ guest memory），覆盖嵌套 record/list/result 组合。
4. 动态调整 STEP-0077–0084。

## 6. 动态优化 M1–M9 的规则

- M1/M2 只在 Script 案例暴露 parser/semantic 缺口时增加回归，不重开已通过的阶段。
- M3/M4 是 M8 主要复用层；任何 Component/package 变化必须保持旧 scalar manifest 与 Runtime 兼容。
- M5–M7 的 Host、registry、trust 状态不因 M8 原型自动升级；公网生产仍等待外部部署输入。
- M8 的排序由 STEP-0076 实测决定：composition 稳定则进入 Adapter 路线，不稳定则选择同 WIT direct runner fallback。direct path 的正确性/延迟证据已具备，composition path 证据缺失是当前唯一缺口。
- M9 继续保持 planned-after-M8；streaming/async/HTTP/REPL 不得混入 M8 bounded batch MVP。
