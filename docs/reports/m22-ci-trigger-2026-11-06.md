## 4. Trigger decision, with reasoning

- `push` → `codex/m22-w2`: added. This is the active M22 line (local branch and
  `github/codex/m22-w2` both at `a939862`), so this is what makes the exit
  audit's exact-SHA independent CI obtainable again.
- `workflow_dispatch`: kept. It is the only way to get a CI verdict on a ref
  that is not the W2 branch (for example an isolated per-slice worktree branch
  such as `codex/m22-w2-step0544`, which STEP-0544 used to keep its evidence
  tree equal to its commit tree while the main worktree had a concurrent
  writer), and it is the escape hatch if a branch name changes again.
- `push` → `dev`: **not added.** Trade-offs considered:
  - For: broader regression coverage; `dev` is the eventual integration target
    named in the M22 delivery description; a `dev` red could surface a
    cross-line break early.
  - Against: the M22 plan decision **D14** (`docs/plans/M22-compiler-self-host.md`)
    rules that M22's completion criteria do **not** include a merge with
    `origin/dev` and forbid rebasing or merging it, recording the conflicting
    history as an M25 integration item. A `dev` push is therefore not M22
    evidence, so a green or red run there would not adjudicate any M22 gate.
    Each run costs roughly one to two hours of a `windows-2025` runner
    (recent adjudicated runs: 57m34s, 1h06m43s, 1h14m36s), so per-`dev`-push
    runs are a real cost with no M22 gate value. A `dev` tree also carries
    other milestones' in-flight work (M24 implementation lives in its own
    worktree, but `dev` accumulates post-M22 lines), which would attribute
    unrelated failures to the M22 track and pollute the CI-history ledger that
    earlier steps maintained run-by-run.
  - Decision: **do not add `dev`.** If the owner later wants a `dev` signal, the
    cheaper and better-scoped options are a separate workflow file with its own
    name, or `workflow_dispatch` against the `dev` ref on demand. Both are
    owner decisions and are not made here.
