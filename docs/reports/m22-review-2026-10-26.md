## 1. 三句话结论

1. 门 2/3 的真实瓶颈不是形状覆盖，而是**装配策略**：guest 发射端用左折叠 `sico.text.concat` 造 hex 文本，输出 N 字节要 O(N²) 次拷贝，而门 3 的目标产物约 1 MiB ⇒ 比已实测的可行上限（S1 128 KiB / S2 256 KiB）高 4–8 倍，代价高 3–4 个量级。
2. 这道墙在 STEP-0516（S5-W1）就已测出并写成「W2/W5 必须遵守的实施约束」，但此后 40 余片从未落到 `selfhost/codegen.sico`（512 处 `sico.text.concat` 引用、461 处自左折叠，原样保留）；最近的 0544/0545/0546 都在优化**查表**（B 路），所以 140 个 `FuelExhausted` 站点**一个都没回绿**（0545 重算仍 32/140/5/219）。
3. 语言面今天已有线性装配所需的全部原语（`sico.list.append` 私有头 + 就地补位 ⇒ 线性 builder 摊还 O(n)，`sico.text.join` 先总长后一次分配 ⇒ O(total)），因此**不需要 RFC、不需要新内建、不需要改 guest ABI**；需要的是把发射端从「字符串累加」改成「分片 list + 一次 join」，并以 1 MiB 产物做验收。

## 3. 墙在装配，不在形状

### 3.1 发射端的输出表示

- `selfhost/codegen.sico`（6,598 行）：194 个 `function`、**512** 处 `sico.text.concat` 引用（**501** 个调用点，其中 **461** 个是 `set X = sico.text.concat(X, …)` 形式的自左折叠）、**0** 处 `sico.bytes.concat`、**0** 处 `sico.text.join`、仅 **3** 处 `sico.list.append`。
- 各节全部产出 **hex 文本**：`cgs_core_type_hex:4900`、`cgs_core_types_hex:4963`、`cgs_core_funcs_hex:5075`、`cgs_core_exports_hex:5143`、`cgs_core_code_hex:6412`。
- 最大的六个累加器：`cbsh_out`（37 处）、`cccsh_out`（32）、`clgh_out`（25）、`cgpr_text`（25）、`ccmh_out`（23）、`cfh_out`（19）；典型写法 `:159-162` `set cgchbh_out = sico.text.concat(cgchbh_out, "200120036a2205")`、`:52` 逐字节 `cg_hex_byte` 追加。
- 也就是说：**每追加一个片段就复制一次已累积的全部内容**。

### 3.2 STEP-0516 的「可行」判读不能迁移到 codegen

`docs/steps/STEP-0516-m22-w2-s5-w1-scale-feasibility.md` 实测三条策略：

| 策略 | 形状 | 结论 |
|---|---|---|
| S1 增量 `sico.text.concat` | 一个累积串迭代拼接 | 128 KiB 用 541,471,259 fuel；**256 KiB ⇒ `arena-exhausted`** |
| S2 `sico.arena.push_chunk` | n 次 push + 末段拼装 | 256 KiB 用 1,085,117,073 fuel；**384 KiB ⇒ `arena-exhausted`** |
| S3 线性对照 | **一次** `concat(left, left)`，两个大操作数**都来自 stdin** | 1 MiB 66 ms / 24,117,785 fuel；4 MiB 133 ms |

- S3 之所以能成立，是因为**两个操作数已经存在**；它测不出「把上千个碎片拼成一个操作数」的成本。发射端做的正是后者，落在 S1/S2 的上限里。
- 源字面量也帮不上：≥1 MiB 的字面量直接撞源契约 `source contract error LineTooLong at bytes 453..1049045`（STEP-0516 §2.2）。
- 因此 §10.10 把 W1 记成「S5-W1 规模可行性：判读为可行」是**口径滑移**：可行的是一次成型的线性组装，不是本节发射端的组装方式。

### 3.3 量级账

- 门 3 目标产物约 1 MiB（§10.1.1 R5）；hex 表示 ⇒ 约 2 MiB 文本。
- 左折叠逐字节拼装 ⇒ 约 2×10⁶ 次 concat、累计拷贝 ≈ (2 MiB)²/2 ≈ 2×10¹² 字节；而 W1 实测 256 KiB（1/4 目标）就已烧掉 1.09e9 fuel 并撞穿 2 GiB arena。按二次律外推，1 MiB 需要 10³ 倍以上燃料与 10² 倍以上时间。
- 反过来：分片 list + 一次 join 的总拷贝 ≈ 输出长度 + 分片表 ≈ 10⁷ 字节量级，燃料回到 STEP-0546 已可达的范围（n=256 指令 9.31 s / 800e9 内）。

### 3.4 为什么 0544–0546 一片站点都没拿到

- STEP-0544：X 族 fuel 曲线只有 `a+b·n+c·n²` 相容（二次项在 n=128 占 86%–97%），A 路是时间墙（每翻倍字面量 ×2.45）。→ 归因正确，但结论落在「修查表」。
- STEP-0545（B1 游标）：二次项系数 0.6×，二次项仍占 76%–97%，**396 站点 verdict 逐条未变**（32/140/5/219）。
- STEP-0546（B2 索引，scratch 树未提交）：n=256 指令进预算（9.31 s），n=512 仍 `FuelExhausted`（94.31 s），账本 36/136/5/219，24,576 B 字面量转绿、32,768 B 仍 trap。
- 读法：查表从 O(n²) 修到 O(n log n) 只换来 0.23×，因为 **O(n²) 的拷贝仍在**。继续修查表就是补丁叠补丁；0546 作者自己已写明「不把 256 回绿外推为大闭包闭合」。

### 3.5 语言面已有线性装配（决定性）

- `crates/sico-codegen-wasm/src/stdlib.rs:596-666`：`list.append` 的私有 16 字节头（magic / used version / capacity / magic2）；命中「调用方持有最新逻辑版本且有空位」时**就地写空位**（`:606-630`），否则按几何翻倍重分配并复制（`:635-641`）。源码注释明写 *"making the common linear builder path amortized O(n)"*（`:600`）。
- `emit_join`（`:670-`）：先扫一遍求总长，再一次分配、一遍拷贝 ⇒ **O(total)**。
- ⇒ 发射端的正确形态是：每条指令/每段产出一个 `Text` 片段，用 `sico.list.append` 收集，末尾 `sico.text.join(chunks, "")` 一次成型。这条路径**今天就能写**，不触碰语言契约。

## 4. 219 个 `closure-too-large` 不是失败，是夹具自设上限

- `runner/sico-runner/tests/selfhost_compiler.rs:9286` `const MATCH_CLOSURE_FUNCTION_LIMIT: usize = 64;`、`:9287` `const MATCH_CLOSURE_BYTE_LIMIT: usize = 262_144;`，在 `:9434` 生成 `closure-too-large:{count}fn/{bytes}B`。
